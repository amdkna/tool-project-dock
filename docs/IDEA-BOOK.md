# Idea Book — Project Dock

> **Product:** Dock by Webigram (Project Dock)  
> **Document type:** Idea Book / Product Vision  
> **Status:** Product vision — not an implementation specification  
> **Updated:** 2026-11-05  
> **Current baseline:** 1.0b (beta)  
> **Planned direction:** 2.0

## 1. ایده در یک جمله

برای **برنامه نویسان تازه کار و Junior** که در مسیر تبدیل ایده هایشان به یک نرم افزار قابل اجرا، با **پیچیدگی و پراکندگی ابزارهایی مثل Git، وب سرور، HTTPS، Docker و CI/CD** روبرو هستند، ما **Project Dock** را می سازیم؛ یک **ابزار جانبی سبک، یکپارچه و ساده برای ویندوز** که بخش بزرگی از کارهای تکراری راه اندازی، مدیریت و اجرای پروژه را به شکل قابل فهم و تا حد امکان خودکار انجام می دهد، تا آنها **به جای درگیر شدن با زیرساخت، زمان و تمرکز بیشتری برای ساخت محصول اصلی خود داشته باشند**.

### نسخه کوتاه ایده

**Project Dock پیچیدگی ابزارهای توسعه را پشت یک محیط ساده و یکپارچه پنهان می کند تا برنامه نویس به جای مدیریت ابزارها، روی ساخت ایده اش تمرکز کند.**

### شعار پیشنهادی

**Less setup. More building.**

## 2. چارچوب ایده: کاربر ← وضعیت ← مشکل ← محصول ← نتیجه

| بخش | تعریف |
|---|---|
| **کاربر (User)** | برنامه نویسان Junior، دانشجویان برنامه نویسی، سازندگان پروژه های شخصی و توسعه دهندگانی که دانش یا تجربه کمی در Git، سرور محلی، Docker و CI/CD دارند. |
| **وضعیت (Context)** | کاربر ایده یا پروژه ای دارد و برای ساخت، تست و اجرای آن روی سیستم خودش باید چند ابزار مختلف را نصب، تنظیم و مدیریت کند؛ گاهی پروژه ها به زبان ها و فریم ورک های متفاوت نوشته شده اند. |
| **مشکل (Problem)** | ابزارهای مورد نیاز پراکنده اند؛ مفاهیم فنی، خطاهای تنظیمات، مدیریت پورت و گواهی، عملیات Git، کانتینرها و اتوماسیون اجرای پروژه زمان و انرژی زیادی مصرف می کنند و مانع تمرکز روی هدف اصلی می شوند. |
| **محصول (Product)** | Project Dock: یک ابزار کم حجم ویندوزی با رابط گرافیکی ساده که مدیریت روزمره Git، اجرای برنامه ها، مسیریابی HTTP/HTTPS محلی، گواهی توسعه، مشاهده و کنترل Docker موجود و اجرای گردش کارهای CI/CD محلی را در یک نقطه جمع می کند. |
| **نتیجه (Outcome)** | کاهش اصطکاک شروع کار، صرف زمان کمتر برای تنظیمات تکراری، کاهش خطاهای معمول، مشاهده روشن وضعیت پروژه و افزایش زمان مفید برای برنامه نویسی، آزمایش ایده و تحویل یک نمونه قابل استفاده. |

### جمله کامل مطابق چارچوب

برای **یک برنامه نویس Junior** که **می خواهد ایده اش را روی کامپیوتر خود به یک اپلیکیشن واقعی تبدیل کند** اما **به دلیل ناآشنایی با ابزارهای Git، وب سرور، Docker و فرایندهای اجرا و انتشار، بخش زیادی از وقتش صرف کارهای جانبی می شود**، ما **Project Dock را به عنوان یک دستیار سبک و یکپارچه مدیریت پروژه های توسعه نرم افزار** می سازیم تا **بتواند بدون یادگیری عمیق همه ابزارهای زیرساختی از همان ابتدا، پروژه را با اطمینان بیشتری مدیریت و اجرا کند و تمرکزش را روی محصول اصلی بگذارد**.

## 3. چرا این محصول لازم است؟

کاربری که تازه توسعه نرم افزار را شروع کرده، ممکن است بتواند با یک زبان برنامه نویسی یا حتی کمک هوش مصنوعی برنامه بسازد، اما برای اجرای همان برنامه با سوال های دیگری مواجه شود:

- کد پروژه را چگونه از GitHub دریافت کنم و تغییراتم را بدون از دست رفتن اطلاعات ارسال کنم؟
- چرا برنامه من روی پورت مورد نظر اجرا نمی شود؟
- چگونه چند اپلیکیشن با زبان های مختلف را همزمان روی localhost اجرا کنم؟
- چگونه برای پروژه محلی خود HTTPS داشته باشم؟
- چگونه بفهمم کانتینر Docker اجرا شده یا چرا متوقف شده است؟
- آیا می توانم قبل از اجرای نسخه جدید، build و test و verify را خودکار انجام بدهم؟
- چگونه وضعیت چند پروژه را بدون باز کردن چندین پنجره و ابزار مختلف ببینم؟

این فعالیت ها ارزش فنی دارند، اما برای کاربر هدف، اغلب **وسیله هستند نه هدف**.

**مشکل اصلی نبود ابزار نیست؛ هزینه یادگیری، اتصال و مدیریت همزمان ابزارهای موجود است.**

## 4. ماموریت و چشم انداز

### ماموریت (Mission)

ساده کردن کارهای عملیاتی و تکراری توسعه نرم افزار در محیط محلی، با یک رابط گرافیکی سبک و قابل اعتماد، بدون تحمیل یک پشته زیرساختی بزرگ به توسعه دهنده.

### چشم انداز (Vision)

تبدیل Project Dock به **میز کنترل محلی پروژه های نرم افزاری**؛ جایی که کاربر مستقل از زبان برنامه نویسی، بتواند پروژه هایش را دریافت، بررسی، اجرا، تست و مدیریت کند، در حالی که ابزارهای اصلی همچنان در پس زمینه و به شکل استاندارد کار می کنند.

### وعده محصول (Value Proposition)

**ابزارهای حرفه ای توسعه، با تجربه کاربری ساده تر و مراحل عملیاتی کمتر.**

Project Dock جایگزین دانش فنی نیست؛ ورود به کار عملی را آسان می کند و در صورت نیاز جزئیات فنی را نیز قابل مشاهده نگه می دارد.

## 5. محصول چه کاری انجام می دهد؟

Project Dock یک **ابزار همراه (companion tool)** است؛ نه یک زبان برنامه نویسی، نه IDE جدید، نه سرویس میزبانی و نه جایگزین موتور Docker.

| حوزه | ارزش برای کاربر | وضعیت |
|---|---|---|
| **مدیریت Git** | دریافت پروژه، Pull، Commit/Push و مدیریت چند مخزن از یک محیط | قابلیت های پایه در 1.0b؛ مشاهده Diff و وضعیت پیشرفته در برنامه v2 |
| **مدیریت پروژه ها** | دیدن پروژه ها در یک محیط و دسترسی آسان به پوشه ها و منابع | پایه موجود؛ ابزارهای تکمیلی برنامه ریزی شده |
| **اجرای اپلیکیشن** | راه اندازی، توقف، راه اندازی مجدد، بررسی سلامت و مشاهده لاگ پروژه های مختلف | برنامه v2 |
| **وب سرور / Gateway محلی** | استفاده از HTTP/HTTPS و هدایت درخواست ها به برنامه هایی با زبان های متفاوت از طریق یک ورودی واحد | برنامه v2 |
| **گواهی HTTPS محلی** | صدور گواهی توسعه Self-signed یا CA محلی با تایید صریح کاربر برای اعتماد به CA | برنامه v2 |
| **Docker Manager** | مشاهده وضعیت کانتینرها، لاگ ها و اجرای Start/Stop/Restart با رابط ساده | برنامه v2؛ نیازمند Docker Engine موجود |
| **Mini CI/CD** | اجرای گردش کارهای سبک Build، Test، Deploy و Verify با تاریخچه و گزارش | برنامه v2؛ اجرا از طریق Agent محلی و SQLite |
| **بررسی سلامت و خطاها** | نمایش روشن مشکلات رایج وابستگی ها، فرایندها و پورت ها | برنامه v2 |

### اصل طراحی مهم

**Dock کنترل کننده است، نه محیط اجرای همه زبان ها.**

برنامه ها می توانند با PHP، Python، JavaScript، TypeScript، Node.js، Go یا زبان های دیگر نوشته شده باشند. اجرای آنها همچنان به Runtime، ابزارهای مربوط یا کانتینر مناسب نیاز دارد. Project Dock فقط مدیریت و هماهنگی کارها را ساده می کند.

## 6. یک داستان واقعی از کاربر

### قبل از Project Dock

یک برنامه نویس Junior با کمک هوش مصنوعی یک وب اپلیکیشن ساده می سازد. برای ادامه کار باید Git را تنظیم کند، مخزن را Clone کند، وابستگی ها را نصب کند، برنامه را اجرا کند، پورت ها را پیدا کند، سرویس محلی را تنظیم کند، شاید HTTPS لازم داشته باشد، Docker را بررسی کند و برای تست و اجرای خودکار چند فرمان بنویسد.

نتیجه این است که با وجود آماده بودن بخش زیادی از کد، ساعات زیادی صرف هماهنگی ابزارها می شود. گاهی اولین تجربه کاربر به جای ساخت محصول، به عیب یابی زیرساخت تبدیل می شود.

### تجربه مورد انتظار با Project Dock

کاربر پروژه را به Dock اضافه می کند، وضعیت Git و ابزارهای لازم را می بیند، فرمان اجرای برنامه را یک بار مشخص می کند و سپس از همان محیط برنامه را اجرا و Preview می کند. در صورت فعال بودن ماژول های مربوط، Route محلی و HTTPS را مدیریت می کند، وضعیت کانتینر را می بیند و یک Pipeline کوچک برای Build/Test/Verify اجرا می کند.

وقتی مشکلی پیش می آید، Dock باید به جای پنهان کردن خطا، وضعیت، لاگ و قدم اصلاحی قابل فهم ارائه کند.

**خروجی مطلوب:** کاربر سریع تر از «کد روی دیسک» به «برنامه قابل مشاهده و قابل آزمایش» برسد.

> این بخش تجربه هدف نسخه های آینده را توصیف می کند و به معنی پیاده سازی همه مراحل در نسخه فعلی نیست.

## 7. اصول محصول

1. **سادگی اولویت دارد:** برای فعالیت های روزمره، رابط قابل فهم و تعداد مراحل کم باشد.
2. **سبک و محلی:** مصرف منابع محدود، اجرای سریع و حداقل وابستگی های اضافی.
3. **چندزبانه بودن پروژه ها:** مستقل از زبان و فریم ورک اپلیکیشن.
4. **اتوماسیون همراه با کنترل:** کارهای کم خطر ساده شوند، اما عملیات مخرب، اجرای اسکریپت ناشناس، تغییر اعتماد گواهی ها و دسترسی های حساس نیازمند تایید روشن باشند.
5. **شفافیت به جای جادوی سیاه:** دستور، نتیجه، وضعیت و خطای فنی قابل مشاهده باشند تا کاربر در صورت تمایل یاد بگیرد.
6. **امنیت پیش فرض:** اطلاعات حساس در فایل های متنی معمولی یا لاگ ذخیره نشوند؛ سرویس مدیریتی به صورت پیش فرض فقط روی Loopback قابل دسترسی باشد.
7. **عدم جایگزینی ابزارهای بالغ:** Git همچنان Git است؛ Docker به موتور موجود متصل می شود؛ Runtime برنامه ها جدا می ماند.
8. **حفظ اطلاعات:** تغییرات محلی، تاریخچه Git، تنظیمات و داده های کاربر بدون اجازه حذف یا بازنویسی نشوند.

## 8. مخاطب اصلی و مرزهای محصول

### مخاطب اصلی

- توسعه دهنده Junior که می خواهد بدون درگیری زودهنگام با DevOps پروژه را اجرا کند.
- دانشجوی برنامه نویسی که چند پروژه کوچک محلی دارد.
- سازنده MVP یا پروژه شخصی که می خواهد سریع آزمایش کند.
- برنامه نویس مستقل که بین چند زبان، پروژه و ابزار رفت و آمد می کند.

### مخاطب ثانویه

مدرسان برنامه نویسی و توسعه دهندگان باتجربه ای که برای پروژه های کوچک به یک کنترل پنل محلی و سبک نیاز دارند.

### این محصول قرار نیست چه باشد؟

- جایگزین GitHub یا یک سرویس Git Hosting.
- جایگزین VS Code یا سایر IDEها.
- جایگزین Docker Engine یا یک Docker Desktop کامل.
- یک Jenkins یا GitHub Actions ابری و همیشه فعال.
- سرور تولیدی یا پلتفرم میزبانی عمومی با تضمین های Production.
- بسته ای حاوی تمام Runtimeها، زبان ها و ابزارهای توسعه.

## 9. محدوده نسخه ها

### وضعیت فعلی: 1.0b (Beta)

طبق مستندات موجود مخزن، قابلیت های پایه مربوط به چند مخزن Git، Add/Clone/Test، Pull، Commit/Push، میانبرهای پوشه و GitHub، مدیریت اعتبار GitHub از طریق Git Credential Manager و ثبت فعالیت ها در محصول وجود دارد.

برچسب نسخه 1.0b به تنهایی به معنی تایید کامل عملکرد روی همه نسخه های ویندوز یا انتشار نهایی فایل اجرایی نیست.

### هدف نسخه 2.0

گسترش Dock از یک ابزار ساده Git به کنترل پنل سبک پروژه های محلی، شامل:

- Agent مستقل از رابط گرافیکی.
- Gateway محلی HTTP/HTTPS با Routeهای قابل تنظیم.
- صدور و مدیریت گواهی های HTTPS توسعه.
- مدیریت اجرای پروژه ها در زبان های مختلف.
- رابط کوچک مدیریت Docker متصل به Engine موجود.
- اجرای Pipelineهای محلی با TOML و ثبت تاریخچه در SQLite.
- بهبود قابلیت های Git، Preview، مدیریت Workspace و تشخیص خطا.

اینها **قابلیت های برنامه ریزی شده** هستند؛ زمان بندی قطعی یا ادعای پیاده سازی محسوب نمی شوند.

## 10. معیارهای موفقیت ایده

برای ارزیابی محصول، باید به جای صرفا تعداد قابلیت ها، اثر واقعی بر تجربه کاربر اندازه گیری شود.

| شاخص | پرسش ارزیابی |
|---|---|
| **Time to First Run** | یک کاربر تازه کار چقدر زمان لازم دارد تا پروژه موجود را به شکل قابل مشاهده اجرا کند؟ |
| **Setup Friction** | برای راه اندازی پروژه چند مرحله دستی و چند ابزار جدا لازم است؟ |
| **Task Completion Rate** | چه درصدی از کاربران بدون کمک بیرونی موفق به Clone، اجرا و Preview پروژه می شوند؟ |
| **Error Recovery** | آیا کاربر از خطاهای رایج توضیح و مسیر اصلاح قابل فهم دریافت می کند؟ |
| **Resource Footprint** | Dock در حالت بیکار و حین فعالیت چقدر CPU و RAM مصرف می کند؟ |
| **Safety** | آیا کاربر می تواند بدون از دست دادن تغییرات محلی یا افشای اطلاعات حساس با ابزار کار کند؟ |

مقادیر هدف باید پس از آزمون با کاربران واقعی تعیین شوند؛ در این مرحله عددی به عنوان نتیجه اندازه گیری شده ادعا نمی شود.

## 11. خلاصه راهبردی

**کاربر:** توسعه دهنده تازه کار یا Junior.  
**وضعیت:** می خواهد ایده اش را به یک اپلیکیشن قابل اجرا تبدیل کند.  
**مشکل:** پیچیدگی، پراکندگی و هزینه یادگیری ابزارهای Git، سرور محلی، Docker و CI/CD تمرکزش را از محصول اصلی می گیرد.  
**راه حل:** یک ابزار جانبی سبک و یکپارچه برای ساده سازی و خودکارسازی کارهای متداول توسعه محلی.  
**نتیجه:** زمان کمتر برای تنظیم زیرساخت، خطاهای قابل فهم تر و تمرکز بیشتر روی ساخت محصول.

### North Star

> **Make local development operations simple enough that the tools stop getting in the way of the idea.**
